# Развёртывание, резервная копия и откат

Порядок для текущего `deploy/docker/docker-compose.server.yml`. Команды выполняются
из корня проекта на целевом сервере. Контейнерный запуск ещё требует проверки;
это инструкция подготовки, а не отчёт о выполненном развёртывании.

Для общего облачного контейнера `deploy/docker/Dockerfile.cloud` сначала подготовьте
[новую базу со словарём и проверенную копию](neon.md). Создание приложения на хостинге
и подключение к внешней БД выполняются отдельно после локальных проверок.

## Render: общий контейнер сайта и API

До создания сервиса соберите и проверьте `deploy/docker/Dockerfile.cloud`, подготовьте
новую Neon по инструкции выше. Только после этого отправьте проверенный локальный коммит
в свою ветку репозитория. Подключение Git Provider и авторизацию выполняет владелец аккаунта.

| Поле | Значение |
| --- | --- |
| Name | `guess-word` либо свободное имя |
| Region | Frankfurt, рядом с выбранной Neon |
| Branch | Проверенная ветка, для первого запуска `main` |
| Language / Runtime | Docker |
| Instance Type | Free; если недоступен, сначала пересмотрите условия и бюджет |
| Root Directory | Пусто |
| Docker Build Context | `.` — корень репозитория |
| Dockerfile Path | `deploy/docker/Dockerfile.cloud` |
| Docker Command | Пусто, используется ENTRYPOINT образа |
| Health Check Path | `/health/live` |
| Auto-Deploy | Disabled до приёмки первой версии |

В Environment задайте `ASPNETCORE_ENVIRONMENT=Production`, `PORT=8080`,
`ASPNETCORE_URLS=http://0.0.0.0:8080`. В `ConnectionStrings__DefaultConnection` поместите
проверенную строку Npgsql с TLS VerifyFull, в `Jwt__Key` — длинный случайный постоянный
ключ. Секретные значения задаются только локально и в панели, не в Git и не в чате.
Если подготовлен `.env.render.local`, он остаётся игнорируемым файлом с правами 600;
переносите из него значения в панель без публикации файла. JWT-ключ сохраняется между
обновлениями, иначе действующие игровые токены перестанут работать.

Нажатие Create Web Service запускает сборку и публикацию. После запуска проверьте
внешний HTTPS-адрес, `/health/live`, `/health/ready`, вложенные страницы и игру по WSS.
Успешный локальный контейнер не заменяет проверку доступности и квот самой площадки.
После приёмки включите On Commit для выбранной ветки; проверка обновлений и отката отдельная.

## Перед первым запуском

- Подготовьте сервер с Docker Compose, доменом и доступными портами 80/443.
- Для приведённой команды публикации клиента нужен .NET SDK из `global.json`.
  Клиент можно заранее опубликовать на машине сборки и передать каталог `publish/client`.
- Создайте защищённый `.env` по `.env.example` с правами `600`; замените пароли и JWT-ключ.
  `GUESSWORD_TLS_DIRECTORY` должен указывать на внешний каталог с `fullchain.pem` и `privkey.pem`.
  Настройте выпуск, автоматическое обновление сертификата и перезагрузку nginx после обновления.
- Передайте `sociation2vec800.vec` отдельно в `src/GuessWord.Api/Resources/Data/`.
- Выберите пустую БД либо согласованный перенос данных. Compose использует PostgreSQL 16;
  совместимость дампа с целевой версией проверьте на отдельной БД до переноса.

API собирается из `src/` текущим Dockerfile, поэтому одной опубликованной DLL для этого
варианта недостаточно. Не передавайте локальные секреты в Docker-контекст.
Подготовка настроек и требования к словарю — в [инструкции запуска](local-run.md).

## Подготовка и запуск

На действующем сервере сначала выполните резервирование ниже и остановите nginx
перед заменой опубликованного клиента. Команды далее применяйте после этих шагов.

```sh
dotnet publish src/GuessWord.Client -c Release -o publish/client
docker compose --env-file .env -f deploy/docker/docker-compose.server.yml config -q
docker compose --env-file .env -f deploy/docker/docker-compose.server.yml build api
docker compose --env-file .env -f deploy/docker/docker-compose.server.yml up -d db
```

Проверьте готовность БД (команда должна завершиться с кодом 0):

```sh
docker compose --env-file .env -f deploy/docker/docker-compose.server.yml exec -T db \
  sh -c 'exec pg_isready -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
```

В серверном Compose `depends_on` задаёт порядок старта, но не ожидает готовности PostgreSQL.
Для переноса сначала восстановите проверенную копию;
API при запуске автоматически применяет миграции и импортирует пустой словарь.

```sh
docker compose --env-file .env -f deploy/docker/docker-compose.server.yml up -d api nginx
docker compose --env-file .env -f deploy/docker/docker-compose.server.yml ps
```

Проверьте HTTPS без отключения проверки сертификата, `/health/live` и `/health/ready` (200),
затем вход, одиночную игру, комнату с друзьями, повторный раунд и переподключение.
Swagger в Production не включён; для проверки используйте клиент и health-маршруты.
Запишите версию исходников, ID образов, дату и результат проверки.

## Резервирование перед обновлением

Остановите приём новых игр и API, оставив БД работающей. Сохраните предыдущие исходники,
конфигурации, опубликованный клиент и образ API по его ID (`docker image save`).
JWT-ключ и настройки подключения сохраните отдельно в защищённом хранилище.
Для custom dump выберите новый абсолютный путь вне проекта; каталог должен существовать:

```sh
umask 077
backup_file=/absolute/path/to/backups/guessword-before-update.dump
docker compose --env-file .env -f deploy/docker/docker-compose.server.yml stop api
docker compose --env-file .env -f deploy/docker/docker-compose.server.yml exec -T db \
  sh -c 'exec pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > "$backup_file" \
  && sha256sum "$backup_file" > "$backup_file.sha256"
```

Продолжайте только при успешном завершении `pg_dump`. Восстановите дамп в отдельную БД,
проверьте аккаунты, историю и словарь, затем испытайте на ней миграции новой версии.
Один хеш подтверждает целостность файла, но не возможность восстановления.
Храните копию вне сервера; до публикации назначьте расписание, срок хранения и ответственного.

## Обновление и откат

После проверки копии подготовьте новый клиент и образ API командами выше, затем запустите
API/nginx и повторите проверку игры. На время замены клиентских файлов остановите nginx;
после замены запустите его заново. Не изменяйте Compose project `guess-word`, volume `pgdata`,
имя БД и major PostgreSQL при обычном обновлении; не выполняйте `down -v`.
`pgdata` — ключ volume в Compose; без переопределений Docker создаёт `guess-word_pgdata`.

При сбое остановите API. Если прежний API совместим с текущей схемой, верните сохранённые
клиент и конфигурации, загрузите прежний образ и задайте его через Compose override `image`
с `pull_policy: never`. Пересоздайте API с `--no-build`, чтобы не заменить образ новой сборкой.
Проверьте готовность и игру до открытия доступа.

Если схема несовместима, возврат одного образа не поможет. Восстановите проверенную копию
в отдельную БД и переключите прежнюю версию приложения на неё, сохранив исходную БД.
Восстановление возвращает данные на момент дампа: последующие изменения нужно сохранить
и согласовать отдельно. Не откатывайте рабочие миграции вслепую.
